# 娱乐模块与“猜股票”Web 端产品、技术及执行计划

> 文档状态：Web 首版已实现并完成本地自检，移动端待后续开发  
> 编写日期：2026-08-28  
> 本期范围：后端 + `moments_web_frontend`，不实现 Flutter 手机端  
> 核心原则：先建设可扩展的娱乐模块内核，再以插件式方式接入第一个游戏模式“猜股票”

## 1. 目标与非目标

### 1.1 本期目标

- 新增“娱乐”一级模块，用户可以浏览、搜索并游玩其他用户发布的游戏。
- 已登录顾客可以创建、编辑、预览、发布、下架自己的游戏。
- 第一个游戏模式为“猜股票”。每个已登录玩家创建的一只虚拟股票，就是该模式下一个独立游戏，拥有自己的配置、场次和排行榜。
- 创作者可选择是否加入 AI 交易者。AI 与当前玩家共同买卖，所有参与者的净买卖量会影响后续股票价格。
- 未登录用户可以游玩公开游戏；服务端通过浏览器访客身份记录场次和排行榜成绩。
- 游戏结算、随机结果、价格变化、交易校验均由服务端裁决，Web 端只负责展示与发起操作。
- 数据结构和代码边界允许后续增加答题、抽卡、竞猜等游戏模式，而不改动通用游戏核心表与核心流程。

### 1.2 本期明确不做

- 不开发 `customer_frontend`、`shop_frontend`、`admin_frontend` 的娱乐模块页面。
- 不接入真实证券行情、真实交易、充值、提现或任何真实资金。
- 本期采用“当前玩家 + 本局 AI”的独立场次，不让多个真实玩家进入同一共享市场。不同真人分别与相同配置的 AI 竞争，并在该股票游戏的独立排行榜比较收益率。
- 不支持玩家之间转账、道具、付费、奖品兑换。
- 不实现连续订单簿、限价单、做空、融资、杠杆、手续费和股息；首版只实现按回合统一清算的轻量市场。
- 不在首版实现创作者脚本或任意表达式，避免任意代码执行和无法审核的规则。

## 2. 产品模型

娱乐模块分为四层，不能把四者混为一张表：

1. **游戏模式 Game Mode**：由代码实现的玩法类型，例如 `GUESS_STOCK`。定义配置结构、校验器、运行引擎和结果计算器。
2. **游戏 Game**：创作者创建的一只虚拟股票，即一个独立“猜股票”游戏，包括股票资料、介绍、封面、可见性、当前草稿等。不同创作者创建的股票不共用价格和排行榜。
3. **游戏版本 Game Version**：一次发布形成一份不可变配置快照。发布后的场次永远绑定该版本，创作者修改后必须发布新版本。
4. **游玩场次 Game Session**：某个登录用户或访客对某个游戏版本的一次独立游玩，记录回合、交易、资产和最终结果。

这样设计后，每只创作股票分别开局、结算和排名；创作者更新事件、AI 或初始价格不会改变正在进行的场次，也不会让历史排行榜失去可解释性。

## 4. “猜股票”完整玩法

### 4.1 创作者配置

#### 基础信息

- 游戏名称：2～50 字。
- 游戏介绍：0～500 字。
- 封面：可选，复用现有上传能力并新增娱乐资源类型。
- 游戏模式：首版固定为“猜股票”，通用层保留其他模式入口。
- 可见性：`PUBLIC`（所有人可见）或 `UNLISTED`（仅链接可玩）；`PRIVATE` 可后续增加。
- 回合数：建议 3～30，默认 10。
- 每回合交易窗口：3～5 秒，默认 5 秒。
- 初始金额：建议 100～10,000,000 虚拟币，最多 2 位小数。
- 是否启用 AI 竞争，以及 AI 数量、难度和风格。

#### 股票配置

一个已登录玩家每创建一只股票，就创建一个独立游戏。一个“猜股票”游戏固定只包含一只可交易股票：

- 股票名称，例如“星际动力”。
- 股票代码，例如 `AERO`，用于游戏内展示。
- 股票类型/板块，例如贵金属、工业、航天；允许创作者从预设类型选择或输入自定义类型。
- 初始价格，必须大于 0，最多 4 位小数。
- 基础波动率：无事件时每回合的最大随机涨跌幅；建议默认 3%，可配置范围 0%～20%。
- 市场流动性：价格抵抗买卖冲击的能力。界面使用“低/中/高”选项，服务端映射为经过校验的市场深度参数，避免要求普通创作者理解公式。
- 最大单回合买卖影响：建议默认 10%，限制大量订单造成价格失控。

首版只允许提交整数股订单，不允许零股、负数持仓和做空。订单在回合截止时按统一的近似成交均价清算。

#### 事件配置

每个游戏可以配置 0 个或任意数量的事件，不设置业务数量上限。每个事件包含：

- 事件名称：2～50 字。
- 事件介绍：0～500 字。
- 发生概率：本回合抽中该事件的概率。
- 影响生效概率：事件已发生后，对当前这只股票实际产生额外影响的概率。
- 影响方向：上涨、下跌或随机。
- 影响幅度：最小百分比和最大百分比，例如 5%～12%。
- 是否启用。

首版每回合最多发生一个事件。所有启用事件的“发生概率”总和不得超过 100%，剩余概率表示“本回合无事件”。这比对每个事件独立抽签更容易解释，也避免同回合出现大量事件造成价格失控。

#### AI 竞争配置

AI 是当前场次内真正拥有现金和持仓的市场参与者，不直接修改价格：

- `AI 开关`：创作者决定是否加入 AI。
- `AI 数量`：建议 1～8 个，默认 3 个。
- `AI 初始金额`：默认与真人相同；是否允许单独设置需确认。排行榜公平模式建议必须相同。
- `AI 难度`：简单、普通、困难。难度只改变策略质量、噪声和反应速度，AI 不得读取未来事件或随机结果。
- `AI 风格`：保守、趋势、逆势、激进、随机。创作者可指定组合，也可使用系统自动组合。
- 每个 AI 只能使用自己的现金、持仓和当时已经公开的价格/事件信息；禁止负现金、裸卖空和无限资金。
- AI 的所有订单与真人订单进入同一交易审计表，并标注参与者身份，确保结算可以复算。

AI 在交易窗口内由服务端按计划时点提交订单。前端可展示 AI 的订单动态、持仓概况和当前资产，但不能在客户端运行 AI，否则刷新、改代码或不同设备会产生不同市场结果。

### 4.2 价格变化规则

当前股票的价格由三部分共同决定：随机基础行情、随机事件、所有参与者的交易净流量。每回合由服务端按以下顺序计算：

1. 每一回合都从 `[-基础波动率, +基础波动率]` 重新随机抽取基础涨跌幅；不是按固定涨跌值或固定曲线变化。
2. 按事件发生概率抽取本回合事件，最多一个。
3. 按“影响生效概率”判断是否叠加事件影响。
4. 事件影响幅度从配置的最小值到最大值之间抽取，并按配置方向决定正负。
5. 汇总当前交易窗口内真人和全部 AI 的订单额：`净买入额 = 总买入订单额 - 总卖出订单额`。
6. 计算订单流影响：`订单流涨跌幅 = clamp(价格冲击系数 × 净买入额 / 市场深度, -单回合影响上限, +单回合影响上限)`。
7. `收盘价 = max(最小价格, 开盘价 × (1 + 基础涨跌幅 + 事件涨跌幅 + 订单流涨跌幅))`。
8. 采用统一近似成交均价：`成交价 = (开盘价 + 收盘价) / 2`，同一回合的真人和 AI 使用相同成交价。
9. 首版建议最小价格为 `0.01`，不出现退市、停牌和负价格。

净买入推动本回合收盘价上涨，净卖出推动本回合收盘价下跌，收盘价成为下一回合开盘价。订单在窗口内只是待清算状态，截止后统一成交。使用开盘/收盘中间价近似本回合成交均价，可以避免玩家按旧价大量买入、完整获得自己制造的涨幅，再在下一回合无风险卖出的明显操纵漏洞。后续若增加连续订单簿和真实滑点，应作为新的规则版本，不直接改变现有场次。

随机数由服务端生成并记录结果。历史回合直接读取已落库结果，不重新随机。后续如需复盘或争议排查，可额外保存经过保护的随机种子或随机证据摘要。

### 4.3 场次状态机

```text
CREATED -> OBSERVING -> TRADING -> CLEARING -> OBSERVING
    |           |           |          |
    +-----------+-----------+----------+-> SETTLING -> COMPLETED
                |           |
                +-> PAUSED <-+
```

为消除“观望期”和“交易期”表述上的冲突，本方案将每个回合拆成两个阶段：

1. `OBSERVING`：服务端公布本回合事件和开盘价，持续建议 1 秒，仅用于信息揭晓，不能交易。
2. `TRADING`：持续创作者配置的 3～5 秒，真人玩家和 AI 提交、修改或撤销本回合订单，页面实时展示市场净流量。
3. `CLEARING`：窗口结束后订单截止；服务端以事件、基础波动和净订单流计算收盘价/统一成交价，再成交所有有效订单。
4. 收盘价成为下一回合开盘价；最后一回合清算完成后直接进入结算。

离开页面时场次进入 `PAUSED`，保存当前回合、阶段、阶段剩余毫秒数、待清算订单、现金、冻结资金、持仓、AI 状态和已产生的随机结果。重新进入该游戏时优先提示“继续游戏”，恢复后从保存的剩余时间继续，而不是重开或补跑离线期间的回合。

正常路由离开使用显式暂停接口；关闭标签、崩溃或断网通过 WebSocket 断开与活动租约/心跳兜底检测。服务端确认暂停后必须同时冻结 AI 决策任务，恢复时再按剩余时间重新调度。由于浏览器异常断开无法保证零延迟，允许在心跳检测窗口内产生最多约 1 秒误差，最终以服务端持久化快照为准。

第 1 回合以创作者设置的初始价格开盘。最后一个交易窗口仍正常清算，其收盘价就是最终结算价，因此最后一回合的真人/AI 买卖同样会影响最终价格；剩余持仓按最终收盘价计入资产，不强制生成一笔卖出交易。

### 4.4 买卖规则

- 每个参与者每回合最多保留一张有效订单，可在截止前修改方向/股数或撤销，避免用大量碎单刷市场流。
- 买入校验：`股数 > 0`，并按当前规则允许的最坏成交价预留足额现金；清算完成后释放剩余预留款。
- 卖出校验：`股数 > 0` 且可用持仓足够；提交后冻结相应股票，撤单或清算后释放。
- 同一请求必须带 `clientRequestId`，服务端做幂等，避免双击或网络重试重复成交。
- 服务端以收到请求时的场次阶段和服务端时间为准；倒计时到 0 后到达的请求拒绝成交。
- 首版订单在回合清算时按统一成交价全部成交，不做部分成交；买入数量上限由预留资金规则提前约束。
- 每场订单修改请求建议限制为 100 次，防止刷接口和推送。
- 金额与价格使用 `BigDecimal/DECIMAL`，禁止使用浮点数直接计算资产。
- 真人和 AI 使用相同的成交、资金和持仓校验服务，不能为 AI 另写一套绕过规则的扣款逻辑。

### 4.5 结算指标

```text
最终资产 = 剩余现金 + 最终价格 × 最终持仓
净收益 = 最终资产 - 初始金额
收益率 = 净收益 / 初始金额 × 100%
```

结算页展示：最终资产、净收益、收益率、该股票游戏的公开排名、本局击败 AI 数量、真人/AI 最终资产对比、现金/持仓变化、逐回合价格曲线、事件、订单流和交易记录。

### 4.6 排行榜

- 每个玩家创建的股票游戏拥有独立排行榜，绝不与其他创作者的股票混排。排行榜底层绑定 `game_id + game_version_id`，默认页面展示当前发布版本。
- 默认按收益率降序，最终资产作为第二排序项，完成时间作为第三排序项。
- 仅 `COMPLETED` 且服务端判定有效的场次进入排行榜。
- 默认每个身份只展示最好的一次成绩，但保留全部历史场次。
- 登录用户显示昵称和头像；访客显示 `游客-xxxx`，`xxxx` 来自访客 ID 的不可逆短摘要。
- 显示前 100 名，并单独返回当前玩家附近名次。
- 创建者自己的正常游玩可以上榜，但应显示“创建者”标记；是否排除仍需产品确认。
- AI 只参与当前场次内的即时竞争，不写入公开玩家排行榜；结算中单独展示“本局第 N/M 名”和“击败 N 个 AI”。这样不会让每一局重新生成的 AI 占据长期榜单。
- 排名局为同一 `game_version_id` 使用服务端保存且不向客户端公开的标准场景种子，使不同玩家面对可比较的随机事件、基础随机序列和 AI 随机源；这仍是逐回合随机取值，不是固定涨跌幅。AI 对玩家行为的合法反应仍可能让最终路径不同。

## 5. 访客身份方案

不使用浏览器指纹。指纹有隐私风险、误识别问题，也不能真正保证唯一。

推荐流程：

1. 首次进入娱乐模块时，前端请求 `POST /api/entertainment/guests`。
2. 服务端生成随机 UUID 访客 ID，并返回短期可续签的签名访客令牌。
3. Web 端将令牌保存在安全 Cookie；若当前部署条件暂时无法使用跨域安全 Cookie，则退化到 `localStorage`，但需要接受 XSS 风险。
4. 后续游玩请求携带访客令牌；登录用户始终以用户 ID 为主身份。
5. 清理浏览器数据、无痕窗口或更换浏览器会形成新访客，这是浏览器标识方案无法避免的边界。

服务端只保存访客 UUID 的哈希或独立随机标识，不保存可用于跨站跟踪的浏览器特征。访客令牌不能获得创建、编辑或管理权限。

## 6. 可扩展技术架构

### 6.1 后端模块边界

建议新增：

```text
backend/src/main/java/com/order/menu/module/entertainment/
  core/
    controller/       通用浏览、版本、场次、排行榜接口
    dto/
    entity/
    mapper/
    service/
    engine/           模式注册、统一生命周期、结算协议
  mode/guessstock/
    config/           GuessStockConfig 及校验
    engine/           回合生成、AI 决策、交易、订单流定价、结算
    dto/
    entity/
    mapper/
  guest/              访客身份签发与解析
```

通用引擎定义稳定接口，例如：

```java
public interface GameModeHandler<C> {
    String modeCode();
    int configSchemaVersion();
    void validateConfig(C config);
    SessionSnapshot initialize(C config, PlayerIdentity player);
    RoundSnapshot advance(SessionContext context);
    ActionResult handleAction(SessionContext context, GameAction action);
    GameResult settle(SessionContext context);
}
```

`GameModeRegistry` 按 `modeCode` 查找实现。通用服务不得 `if (mode == GUESS_STOCK)`，避免每增加一种游戏就修改核心流程。

### 6.2 配置存储策略

- `game_versions.config_json` 保存已发布的完整、不可变模式配置。
- 同时保存 `config_schema_version`，模式处理器负责读取当前仍支持的旧配置版本。
- 通用字段使用关系型列，便于筛选和索引；模式专属的创作配置使用 JSON，避免核心表随模式增长。
- 高频运行数据如回合、持仓、交易、排行榜使用独立关系表，不能全部塞入 JSON。
- 发布时对配置做严格 DTO 反序列化与白名单校验，不接受任意未知表达式或类名。

### 6.3 时间与并发

- 服务端是唯一时钟。活动场次响应返回 `serverTime`、`phaseEndsAt`；暂停场次返回 `phaseRemainingMs`，恢复时由服务端重新生成截止时间。
- Web 端只用服务器时间差渲染倒计时，不能自行决定回合结束。
- 场次推进使用数据库乐观锁 `version` 或带条件更新，确保并发请求只推进一次。
- 真人和 AI 交易都在事务内锁定对应参与者的资产/持仓记录，完成阶段校验、扣款和成交落库。
- AI 决策任务必须使用唯一任务键，重复调度不能产生重复订单；阶段结束后未执行的 AI 任务自动失效。
- 暂停与恢复使用场次乐观锁原子更新；暂停成功后 AI 任务不得继续下单，恢复时不得重复执行暂停前已完成的任务。
- 定时任务用于主动推进活跃场次；接口访问时再做一次惰性推进，避免任务延迟导致卡局。
- Redis 只承担活跃场次加速、倒计时通知和限流，MySQL 是最终事实来源；Redis 故障不能丢失成绩。

### 6.4 通信方式

场次创建、真人交易、同步和结算使用 REST。AI 订单、市场净流量、阶段变化优先复用现有 WebSocket 推送，以便 3～5 秒窗口内及时展示竞争动态；断线时前端退化为短轮询，恢复后以 REST 场次快照覆盖本地状态。

WebSocket 只传递变化通知，不作为最终事实来源。后续若增加多个真实玩家同场或观战，可继续扩展 `GAME_SESSION` 目标类型，但需要新增共享市场和房间状态机，不能把独立场次直接拼在一起。

### 9.1 娱乐广场

- 顶部提供关键词、游戏模式、排序筛选；主体是可扫描的游戏列表。
- 游戏项就是一只由玩家创建的虚拟股票，展示封面、股票名称/代码、类型、创作者、是否有 AI、游玩数、当前版本和“开始游戏”。

### 9.2 创建/编辑页

- 使用分区表单：基本信息、股票、回合、事件、资金、发布检查。

- 概率旁实时显示总和与“无事件概率”。
- 提供配置校验摘要和预览试玩，发布前列出阻断错误。
- 已发布版本不可直接覆盖；再次发布明确提示将生成新版本。

### 9.3 游玩页

- 桌面端主区域展示稳定尺寸的单股票价格折线图、本回合事件、市场净买卖流和 AI 订单/成交动态。
- 侧栏展示倒计时、现金、总资产、持仓、买卖控件，以及当前真人/AI 资产排名。
- 买入/卖出使用分段控件，股数使用数字输入与最大可买/全部卖出快捷命令；清楚区分“待清算订单”和“已成交”，允许截止前改价量或撤销。
- 阶段切换不能引起布局跳动；事件揭晓、成交成功、请求失败有清晰但克制的反馈。
- 页面隐藏或网络断开时，恢复后立即向服务端同步，不在本地补算价格。
- 离开游玩页时暂停场次；再次打开游戏详情或游玩页时检测未完成场次并提供“继续游戏”，恢复原阶段和剩余倒计时。

### 9.4 结算与排行榜

- 结算先展示收益率和最终资产，再展示排名、曲线、事件和交易复盘。
- 排行榜明确标注股票游戏、创作者、版本号、排名口径、访客身份和创建者身份；不同股票游戏绝不混排。
- 对未完成、失效、作弊判定的场次展示原因，不进入榜单。

“只完成 Web 端”包含桌面和手机浏览器响应式体验，本期验收 1440px、1024px、390px 和 375px；不实现 Flutter 原生客户端。

## 10. 安全、风控与合规

- 所有页面醒目标注“虚拟行情、虚拟资产，仅供娱乐，不构成投资建议”。
- 游戏名称、描述、股票名、事件名均做长度限制和输出转义，禁止 HTML/脚本。
- 创建、发布、开始场次、交易接口分别限流；访客按访客 ID + IP 辅助限流，IP 不作为身份。
- 服务端禁止返回未来回合结果或可预测的随机种子。
- 发布配置需要大小上限，建议 JSON 不超过 128 KB。
- 排行榜记录只接受服务端结算结果，客户端不能直接上报分数。
- 游戏下架后禁止新开局，已开始场次默认允许完成；封禁游戏的处理规则需由管理员策略决定。
- 用户游戏发布后立即公开，不走预审；管理员必须具备强制下架能力，发布接口需要文本校验、频率限制和审计记录。
- 访客数据设置保留期限并提供清理任务；具体期限需确认隐私政策后确定。

## 12. 测试矩阵与验收场景

### 12.1 后端重点测试

- 配置：0 个事件、概率总和等于/小于/大于 100%、影响上下限反转、AI 开关/数量/策略组合、非法市场深度。
- 随机：固定种子结果稳定；事件未命中、事件命中但影响未生效；AI 只能读取当时公开信息。
- 市场影响：净买入推动上涨、净卖出推动下跌、买卖相抵、零流量、极端流量受单回合上限保护。
- 金额：恰好花完、余额差 0.01、超卖、价格跌到下限、大金额无精度丢失。
- 时间：截止前成交、截止瞬间、截止后拒绝、服务器任务延迟后惰性推进。
- 暂停：正常离页、WebSocket 异常断开、活动租约过期、重复暂停/恢复、剩余时间精度、暂停期间 AI 不下单且价格不推进。
- 并发：双击买入、AI 任务重复触发、真人与 AI 同时成交、两个标签同时交易、两次推进、重复结算只产生一个榜单条目。
- 权限：访客不可创建、他人不可编辑、下架后不可开局、客户端不可指定身份和分数。
- 版本：旧场次读取旧配置，新版本排行榜与旧版本隔离。

### 12.2 Web 重点测试

- 创建器可访问性、键盘操作、长名称、空状态、概率错误定位。
- 服务端时间差、后台标签恢复、刷新恢复、断网重试、重复提交。
- 交易按钮在错误阶段、余额不足、持仓不足时正确禁用并显示原因。
- 图表在无变化、大幅涨跌和连续触及保护值时正确显示；AI 成交和净买卖流不会造成布局跳动。
- 登录用户和访客的开始游戏、历史、排行榜身份展示正确。

### 12.3 MVP 端到端验收

1. 登录顾客创建一只含 5 个事件、10 回合、3 个 AI 的股票游戏并发布。
2. 未登录浏览器无需登录即可开始游戏，获得游客身份。
3. 玩家与 AI 在多个回合买卖；玩家中途离开后场次暂停，重新进入可从原阶段和剩余时间继续，暂停期间 AI、订单和价格不变化。
4. 事件和真人/AI 订单净流量共同决定本回合收盘价，收盘价成为下一回合开盘价；客户端和 AI 都不能提前读取未来事件。
5. 最后一回合自动结算，展示玩家在本局 AI 中的名次，收益明细可复算，真人成绩进入该股票游戏的正确版本排行榜，AI 不进入公开榜单。
6. 另一名用户创建的股票拥有完全独立的场次与排行榜。
7. 创作者修改配置并再次发布后，新旧场次和排行榜互不污染。

## 14. 产品边界确认记录

### 14.1 已确认的核心规则

1. 每个已登录顾客创建的一只股票，就是“猜股票”类别下的一个独立游戏，并拥有独立排名；一个游戏不配置多只股票。
2. 每场只有当前真人玩家与本局 AI，不包含其他在线真人的共享市场。
3. 每回合先进行 1 秒信息揭晓，再进行创作者设置的 3～5 秒交易。
4. 交易窗口内可以提交、修改或撤销订单；截止时净订单流决定收盘价，所有参与者按开盘/收盘中间价统一成交。
5. 每回合最多发生一个事件；事件的发生概率、影响生效概率和影响幅度均可配置。
6. 没有事件或事件未生效时价格仍会变化；基础涨跌幅每回合重新随机生成，不使用固定变化。
7. AI 只作为当前场次对手并参与本局名次，不进入该股票游戏的长期公开排行榜。
8. 排名局可以使用服务端标准场景种子，让不同玩家面对可比较的随机序列；随机涨跌值仍逐回合生成，不是固定涨跌率。
9. 离开页面后暂停并保存当前进度；再次进入时继续当前回合、阶段和剩余时间，离线期间真人、AI 和价格都不推进。
10. 只有已登录顾客可以创建和发布股票游戏；访客仍可游玩公开游戏。
11. 每只股票游戏独立按收益率排名。
12. 游戏发布后立即公开，不经过人工预审；管理员保留强制下架和审计能力。

### 14.2 未指定细节的推荐默认值（非阻断）

1. 游戏名称、介绍、事件数、AI 数量、回合数和金额的上下限。
2. 股票最小价格、价格和金额保留位数、涨跌幅最大值。
3. 市场深度由创作者选择“低/中/高”，还是允许高级模式输入具体数值；本方案建议首版只提供选项。
4. AI 初始金额必须和真人相同，还是创作者可单独配置；本方案建议排名局必须相同。
5. AI 是否展示完整现金和持仓，还是只展示成交与资产估值；本方案建议展示资产和最近成交，不公开策略内部状态。
6. 事件在结算复盘中展示全部细节，还是只显示玩家当时看到的信息。
7. 创建者成绩是否进入榜单；游客是否与登录用户同榜。
8. 登录后是否把当前浏览器的游客历史合并到账号，以及合并是否包含榜单成绩。
9. 一个玩家能否同时开始同一股票游戏的多场，还是只能存在一个进行中场次。
10. 游戏下架后，已开始场次能否继续；本方案默认可以完成。
11. 排行榜刷新频率、前台缓存时间、历史版本是否可切换查看。
12. 是否提供游戏点赞、收藏、评论、举报、分享和推荐排序；本期均未纳入核心范围。
13. 访客数据和未完成场次的保留期限，建议结合隐私政策与数据库容量确定。

## 15. 已确认的首版决策摘要

- 一个已登录顾客创建一只股票即形成一个独立游戏，每局只交易该股票。
- 每位真人独立开局，可选择是否加入 AI；市场参与者只有当前玩家和本局 AI。
- 1 秒事件/价格揭晓，随后由创作者设置 3～5 秒交易；离开页面暂停并保存，回来继续。
- 每回合最多一个事件；事件发生概率、生效概率和影响幅度均可设置；无事件也会随机变化。
- 窗口内提交、修改或撤销订单，截止时统一清算，真人与 AI 的净买入/卖出决定收盘价，统一按开盘/收盘中间价成交。
- 订单流价格影响由市场深度和单回合上限约束；AI 只使用已公开信息，不读取未来事件。
- 只有已登录顾客可创作；访客和登录用户都可游玩；访客不可创作。
- 游戏发布后立即公开，但管理员具备强制下架能力，并限制文本与发布频率。
- 每只创作股票分别建立排行榜，并按版本隔离，以收益率排序；AI 仅参与本局排名，不进入公开榜。
- 排名局使用服务端标准场景种子保证可比性，基础价格仍按随机序列逐回合变化。
- 清理浏览器数据会生成新访客身份，不承诺跨浏览器唯一。
- Web 桌面和手机浏览器共同验收；Flutter 原生客户端列入后续版本。

### 17.1 导航与整体 UI

### 17.2 事件新规则

- 取消“所有事件发生概率总和不得超过 100%”规则。每个尚未发生的事件按自己的回合发生概率独立判定，不继承其他事件的概率权重。
- 同一场游戏中，已发生事件从后续回合候选池移除，不能再次发生；仍允许整个回合没有事件。
- 首版建议保持每回合最多一个事件：若同一回合有多个剩余事件判定命中，从命中集合中再随机选择一个，其余事件仍保留到后续回合。该冲突处理需最终确认。
- 事件出现后进入无倒计时的 `EVENT_ACK` 阶段，弹窗展示名称、解释和影响是否已生效；单人必须点击“已知晓”才进入交易倒计时。
- 多人房间要求全部当前有效真人成员确认；AI 不参与事件确认。成员状态、确认时间和幂等请求均由服务端保存。
- 创建器支持 CSV 导入事件：下载 UTF-8 BOM 模板、选择文件、列校验、逐行错误提示、导入预览、确认后覆盖或追加。建议列为 `name,description,occurrenceProbability,effectProbability,direction,minImpactPercent,maxImpactPercent,enabled`。

### 17.3 回合与推进

- 提高回合数和交易秒数上限；最终上下限待确认，建议回合 `3～200`，交易时间 `3～300` 秒。
- 游戏增加 `AUTO` 与 `MANUAL` 推进模式。自动模式在交易截止并完成清算后进入下一回合；手动模式清算后进入 `ROUND_READY`。
- 单人手动模式由真人点击“下一回合”；AI 完成本回合决策和清算后自动就绪。
- 多人手动模式要求全部当前有效真人成员就绪后推进；AI 只要本回合任务已结束即自动就绪。
- 需要定义成员断线、长期不确认事件或不点击下一回合时的移除/超时策略，避免整个房间永久阻塞。

### 17.4 真正的模型 AI

- 开启 AI 后不再只使用内置随机策略；服务端通过模型 API 请求生成买入、卖出、持有、股数和简短理由，再按现金、持仓、阶段和最大订单限制二次校验。
- 建议首版采用 OpenAI-compatible 协议，配置 `baseUrl`、`model` 和 API Key；密钥不得写入游戏配置 JSON、版本快照、日志或返回给其他玩家。
- API Key 的费用承担者和生命周期仍需确认。推荐“每个实际玩家为自己的场次提供 Key，服务端仅按场次加密保存并在结束后清除”，避免公开游戏无限消耗创作者 Key。
- 模型超时、限流、非法 JSON 或不可用时需要明确策略。建议该 AI 本回合执行 `HOLD` 并展示失败状态，不回退成隐藏的随机策略。
- 需要增加调用超时、每场/每回合调用上限、响应审计（不含 Key）、提示词版本和模型输出 schema。

### 17.5 多人房间

- 新增多人玩法开关。创建房间后生成短邀请码，其他登录用户或访客输入邀请码进入等待大厅，房主开始后锁定成员列表。
- 多个真人和本局 AI 共享同一股票、事件、回合、订单净流量和收盘价；每个参与者仍拥有独立现金、持仓、订单和最终收益率。
- 房间需要成员、房主、加入/退出、在线租约、准备、事件确认、下一回合投票和邀请代码唯一性数据模型；当前单人 `game_sessions.player_identity_key` 不能直接承担多人授权。

## 18. 2026-08-28 第二轮交互修订（覆盖 17 节冲突项）

### 18.1 已确定规则

- 回合产生新事件时进入 `EVENT_ACK`，弹窗只显示事件名称和解释，并暂停自动模式计时；单人点击“我已知晓”后继续，多人等待全部有效真人确认。确认后盘面仍提供事件按钮随时回看；无事件时不阻塞并明确显示“本回合无事件”。
- 清算之前，接口不返回事件是否产生价格影响、随机后的实际方向和事件影响幅度；清算完成后用顶部短横幅显示自然结果，例如“原料短缺发生，导致股价下跌 2.40%”，不使用抽象的“生效/未生效”文案，也不弹出阻塞弹窗。
- 事件发生改为“候选优先”：每回合从尚未出现的启用事件中随机选择一个候选，再按该候选自己的发生概率掷一次。事件数量增加不会将整回合触发率叠加到接近 100%；实际出现过的事件仍从后续候选池移除。
- 事件数量不设业务上限；手动添加和 CSV 批量导入都可持续追加，服务端只逐项检查名称、概率、方向和影响幅度，不按事件总数拒绝保存或发布。
- `MANUAL` 模式不设置揭晓或交易截止时间，进入回合后直接开放交易。单人点击盘面“下一回合”后立即截止并清算；多人要全部有效真人点击后才截止订单、执行剩余 AI 决策并清算。已经确认的玩家不能再修改或撤销订单。
- `AUTO` 模式继续使用 1 秒揭晓和创建者设置的交易秒数，到时统一清算并自动进入下一回合。
- 走势图从开局起按配置总回合数固定横轴，分段显示涨跌颜色，提供悬停/触控十字线和信息提示，并标记当前玩家最近的买入、卖出成交。
- 下跌线段下方使用淡红色区域、上涨线段下方使用淡绿色区域；普通价格点缩小，悬停命中的点平滑放大，避免高回合数时白点过密。
- 新产生的上涨、下跌和平盘线段均使用绘制动画进入，下跌线段使用稍长的缓动以便清楚看到价格向下形成；动态同步只为新增线段播放，不反复重播历史走势。
- 完成结算后提供“重新开始”。无 AI 游戏直接创建新场次；有 AI 游戏重新选择模型服务并输入 API Key，因为上一局凭据已按规则清除。
- 游玩中的单人“重新开始”直接重置当前场次；多人显示重开投票，全部有效真人都同意后才统一重置，重置前可以撤销自己的申请。重置清空行情、订单、成交、资产与持仓，但保留当前多人房间和本局 AI 凭据。
- 手机 Web 的交易订单直接位于走势图下方，买入和卖出仍同时展示；原“手机端后续实现”仅指 Flutter 原生页面，不再包括手机浏览器响应式页面。
- AI 配置提供 OpenAI、DeepSeek、阿里云百炼、Moonshot、智谱 AI、硅基流动和自定义兼容接口；模型名仍允许用户填写，以免供应商模型列表更新导致前端失效。
- AI 决策新增最近 8 回合走势、平均持仓成本、剩余回合、公开买卖流量、当前资产排名和已公开事件语义，并明确中间价与自我价格冲击规则；难度控制策略稳定度，模型结果仍经过现金、持仓和订单上限校验。
- 下单阶段的开盘价只用于估算金额与冻结资产。收盘价由基础波动、事件和净订单流共同确定，买入和卖出最终都按 `(开盘价 + 收盘价) / 2` 成交，不采用“买入按开盘、卖出按收盘”的非对称规则。

### 18.2 仍需后续确认的边界

- 候选事件当前采用等概率选择，再使用候选自身发生率。若未来希望某些事件更常被“候选”，应另增候选权重字段，不能复用发生率同时表达两个含义。
- 多人手动模式仍永久等待全部有效真人；沿用断线 60 秒后房主可移除的规则，暂不提供房主强制清算。
- 模型服务预设地址属于客户端便利项，服务商模型下线、区域限制、额度、内容审查和限流由用户自己的账号承担；服务端仍只接受公开 HTTPS 地址并保留 SSRF 防护。

### 18.3 本轮自检

- 后端全量 `mvn test` 覆盖事件池频率不叠加、事件不重复、统一中间价、AI 输出校验与决策上下文；V21 增加多人重新开始投票状态。
- 实际 REST 验证事件阶段没有截止时间且清算前隐藏实际影响；手动场次进入 `TRADING` 时 `phaseEndsAt = null`；单人可原地重置当前场次，多人必须全员投票。
- `moments_web_frontend` 生产构建及娱乐专项 Playwright 覆盖桌面/390px 手机走势图悬停、事件暂停弹窗、绘线动画、成交价说明、单人进行中重开、买卖双面板、手机交易面板顺序、无横向溢出和无控制台错误。

## 19. 2026-08-28 双阶段交易修订（最终覆盖第 17、18 节冲突项）

### 19.1 已执行方案

1. V23 将每回合拆成开盘前买入与收盘前卖出两个子阶段，订单、AI 任务、事件确认和多人就绪都增加阶段维度。
2. 开盘价按上一收盘价、开盘事件和全场买入股数/流动性计算，买单按开盘价成交；收盘价按开盘价、基础随机、沿用或新抽事件、全场卖出股数/流动性计算，卖单按收盘价成交。
3. 新增 `marketLiquidityShares`，默认 1,000 股/参与者、可配置 100～10,000,000；价格冲击仍受 `maxOrderImpactPercent` 上限约束。
4. 开盘事件若出现则收盘延用且不再抽取；开盘无事件才在收盘前再次执行候选优先的独立抽取。一个完整回合最多一个实际事件。
5. 事件、开盘结果和收盘结果均使用阻塞弹窗；自动模式只自动截止交易窗口，关键结果仍由真人确认。手动模式没有交易倒计时。
6. 当前回合的开盘/收盘节点只在对应价格生成后绘制，走势图不提前画未来点；开盘、收盘节点与当前玩家买卖成交分别关联。
7. 重开改为确认后结束当前场次并返回游戏详情主界面。多人仍需全体有效真人确认，完成前界面显示确认名单。
8. 手机 Web 重排为行情摘要、走势图、交易面板的连续顺序，新增收益率，走势图使用独立最小高度而非直接压扁桌面比例。
9. 旧的“净订单中间价统一成交”“买卖同时提交”“原地复用场次重开”规则全部废止。

### 19.2 验收结果

- REST 已验证：开盘阶段订单 `stage=OPENING`，1500 股买盘在 1000 股流动性和 10% 上限下将 100.00 推至 110.00；买单按 110.00 成交后现金可为负；收盘阶段订单 `stage=CLOSING`，卖单按最终收盘价成交并正确减少持仓。
- `moments_web_frontend` 生产构建通过；专项 Playwright 完整经过事件确认、开盘买入、开盘结果、收盘卖出、收盘结果、下一回合、图表悬停、390px 布局和确认重开返回详情，浏览器控制台无错误。
- 桌面和手机截图位于 `moments_web_frontend/test-results/entertainment`。

### 19.3 未决边界
