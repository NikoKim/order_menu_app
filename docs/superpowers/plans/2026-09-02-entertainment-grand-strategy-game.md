# 娱乐模块军事策略游戏详细方案

> 文档状态：待评审、待实施
> 编写日期：2026-09-02
> 暂定游戏名：国策沙盘
> 模式代码：`GRAND_STRATEGY`
> 游戏分类：`STRATEGY`（军事策略）
> 实施范围：`backend` + `moments_web_frontend`，原生 Flutter 客户端另行排期
> 产品定位：把《钢铁雄心》式战争、生产与后勤，和《维多利亚》式经济、人口与政治取舍，压缩成一局 30～60 分钟的回合制大战略游戏

## 1. 结论与推荐范围

本方案不是复制任何现有游戏的地图、国家、数值、界面、文本或美术，而是提取“国家经营、经济转军工、政治集团、外交博弈、战线与补给”这些类型玩法，制作一个原创、架空、适合浏览器的轻量模式。

推荐先交付一个真正能完整通关的纵向切片，而不是第一版就制作几千省份、数百商品和即时战斗：

- 娱乐首页仍为同一个 `/customer/entertainment` 页面，在页面内以“全部游戏 / 金融模拟 / 军事策略”一级分类区分股票游戏和军事策略游戏。
- 新增 `GRAND_STRATEGY` 模式，首发一个官方架空剧本“裂洲纪元”：6 个国家、18 个地区、24 回合，每回合代表一个季度。
- 玩家控制一个国家；其余国家由确定性规则 AI 控制。第一阶段支持单人，第二阶段扩展 2～4 名真人同局，其余国家仍由 AI 接管。
- 经济只保留人口、粮食、煤炭、钢铁、石油、国库、民用产能、军用产能和运输能力；政治只保留稳定度、合法性、战争支持度与 5 个利益集团。
- 军事不模拟单兵或数十个师，玩家管理“集团军”，在战线上选择固守、推进、重点突破或撤退，服务端统一结算。
- 首版不使用大模型决定国家行动。核心 AI 使用可复算的效用 AI；大模型以后只可用于可选的新闻文案和角色化外交表达，不参与胜负裁决。
- 服务端保存权威状态、随机种子、玩家命令和结算明细；刷新、暂停、恢复后结果必须一致，前端不得自行结算。

第一阶段应把单局体验做完整；自定义地图、复杂海空军、完整玩家剧本编辑器和多人长局不进入最小可玩版本。

## 2. 为什么这样简化

大战略游戏最容易失控的地方不是功能数量，而是系统之间的乘法效应。经济、政治、外交、后勤、战争每增加一层自由度，AI、平衡、解释性和存档兼容成本都会同时增加。因此本游戏保留以下核心决策：

1. 是优先改善民生、积累国力，还是提前扩军。
2. 是提高税收承受短期不满，还是举债维持支出。
3. 是依赖进口，还是争夺关键资源地区。
4. 是安抚利益集团换取稳定，还是推行高收益但有阻力的改革。
5. 是分兵守住整条战线，还是集中补给打一个突破口。
6. 是通过贸易和条约建立安全网，还是冒着制裁与战争疲劳扩张。

删除或延后以下高成本内容：

- 逐人口单位的职业、宗教、文化和迁徙模拟。
- 逐师编制、装备型号、师级微操和小时级推进。
- 全球真实历史地图、真实国家与历史事件树。
- 独立海战棋盘、舰船设计器、空军联队微操。
- 自由绘制地图、自由脚本和任意公式。
- 实时暂停制。Web 首版采用同时规划、统一结算的回合制。

## 3. 与现有娱乐模块的关系

### 3.1 需要复用的通用能力

现有娱乐模块已经具备以下可复用资产：

- `games`：游戏条目、作者、标题、封面、可见性与发布状态。
- `game_versions`：不可变规则快照与剧本种子。
- `game_sessions`：玩家身份、场次状态、当前回合、暂停与恢复。
- `game_session_actions`：带 `clientRequestId` 的幂等操作审计。
- `game_rooms`、`game_room_members`：房间、邀请与成员身份。
- `game_leaderboard_entries`：版本排行榜。
- `GameModeRegistry`、`GameModeHandler`：模式注册、配置校验与卡片摘要。
- 访客身份、游玩密钥、作者发布和历史记录。

军事策略模式不得复制一套 `strategy_games`、`strategy_versions` 或访客系统；它只增加模式专属运行表和运行引擎。

### 3.2 当前代码在接入第二种模式前必须解决的问题

虽然数据模型已经按模式分层，当前运行接口仍明显绑定“猜股票”：

- `EntertainmentController` 直接依赖 `GuessStockSessionService`，开始、同步、行动、暂停、恢复、历史与排行榜都没有按 `modeCode` 分派。
- `EntertainmentDtos.SessionResponse` 内含 `GuessStockConfig`、股票回合、订单、成交、贷款和 AI 投资观点，不能作为军事策略响应。
- `GameSummaryResponse` 把 `stockCode`、`stockType`、`aiEnabled` 等股票字段放在通用 DTO 顶层。
- `EntertainmentGameService.list` 只有 `stockType` 筛选，而且在数据库分页后于 Java 内过滤，会造成多模式分页数量不准确。
- Web 路由把所有场次固定指向 `GuessStockPlay.vue`，游戏详情、编辑器、说明书和“创建股票”文案也默认只有股票模式。

因此不能只增加几张军事表和一个页面。实施顺序必须先完成一次保持股票行为不变的轻量多模式改造，再接入新引擎。

## 4. 娱乐首页与分类设计

### 4.1 页面信息架构

同一个 `EntertainmentHub.vue` 页面按两层筛选组织，不新增独立军事游戏广场：

```text
娱乐
├─ 一级分类：全部游戏 | 金融模拟 | 军事策略
├─ 搜索、排序、刷新
├─ 二级筛选：随当前一级分类变化
│  ├─ 金融模拟：全部板块 | 贵金属 | 航天 | 工业 ...
│  └─ 军事策略：全部规模 | 短局 | 标准局 | 多人
└─ 混合游戏列表
```

一级分类必须是明确的分段控件，不把军事策略误做成与“贵金属、工业”平级的股票板块。URL 同步查询参数，例如：

```text
/customer/entertainment?category=STRATEGY
/customer/entertainment?category=FINANCE&mode=GUESS_STOCK
```

刷新和分享链接后应保留当前分类、模式、排序和关键词。

### 4.2 首页文案和操作

- 页面副标题改为通用文案，例如“选择一种规则，开始一局可保存、可复盘的游戏”。
- “玩法说明”改为“游戏说明”，先打开模式选择，再展示对应说明书。
- “多人游戏”先让用户选择游戏类别或直接输入邀请码；输入邀请码后由服务端识别房间所属模式。
- “创建股票”改为“创建游戏”。点击后先进入模式选择页，再进入股票编辑器或军事剧本编辑器。
- “我的游戏”和“游玩记录”显示模式图标、分类、模式名，不使用股票专属字段。

### 4.3 卡片差异

两类游戏使用相同卡片骨架，但摘要不同：

| 内容 | 猜股票 | 军事策略 |
| --- | --- | --- |
| 类别标识 | 金融模拟 | 军事策略 |
| 主视觉 | 股票代码与趋势图标 | 架空地图缩略图与旗帜色块 |
| 摘要 | 板块、回合数、AI 数量 | 国家数、地区数、回合数、预计时长 |
| 标签 | 市场版本、贷款/研究 | 经济深度、战争强度、单人/多人 |
| 主命令 | 查看并开始 | 选择国家并开始 |

卡片颜色不能仅靠颜色区分类别；同时显示模式图标和文字。封面缺失时军事模式使用内置架空地图缩略图，不引用现有商业游戏素材。

### 4.4 后端列表接口

`GET /api/entertainment/games` 增加：

- `category`：`FINANCE`、`STRATEGY`。
- `modeCode`：`GUESS_STOCK`、`GRAND_STRATEGY`。
- `features`：可选，例如 `MULTIPLAYER`、`SHORT_SESSION`。
- 继续保留 `stockType` 一版兼容，但只对 `GUESS_STOCK` 生效。

模式和分类筛选必须在 SQL 分页前完成。第一版可以把分类对应到模式代码集合；当模式数量增加后，再考虑把 `category_code` 冗余到 `games` 表并建立索引。

## 5. 游戏世界与首发剧本

### 5.1 原创架空设定

首发剧本暂名“裂洲纪元”，使用原创大陆和国家，避免现实政治争议与历史还原成本：

- 6 个可选国家，各有明显但不过度不对称的起始条件。
- 18 个地区，每国初始拥有 3 个左右；地区通过邻接图连接。
- 4 个海域只作为贸易通道与封锁修正，不制作独立舰队棋盘。
- 24 回合，每回合一个季度，完整覆盖 6 年。
- 前 2 回合默认禁止主动宣战，让玩家熟悉经济和部署；剧本可配置关闭。

六国原型只描述制度和资源特征，不影射现实国家：

| 国家定位 | 优势 | 短板 | 推荐玩法 |
| --- | --- | --- | --- |
| 工业联邦 | 民用工厂多、科研快 | 石油不足、党争明显 | 贸易与技术 |
| 北境共和国 | 钢铁与防御地形 | 人口少、财政弱 | 防守反击 |
| 海湾同盟 | 石油、贸易收入高 | 陆军规模小 | 外交与机动战 |
| 高原公社 | 人口和稳定度高 | 工业落后 | 长期建设 |
| 王冠帝国 | 现役军力强 | 债务高、改革阻力大 | 早期扩张 |
| 南陆议会 | 粮食、人口和联盟能力 | 军工不足 | 经济与联盟 |

具体名称、美术和数值在内容制作阶段确定，上表只定义玩法角色。

官方剧本也作为一条普通 `games + game_versions` 记录参与列表、开局和版本管理，但不能在迁移脚本里硬编码某个真实用户 ID。建议创建一个禁止登录的“官方内容”系统账号作为 `creator_user_id`，并在 `games` 增加 `publisher_type=SYSTEM/USER` 与 `system_managed` 标记。普通作者接口永远不能编辑或删除 `system_managed=1` 的游戏；官方发布通过受控初始化器或管理员命令执行。这样既保留现有非空外键和作者展示，又不会把官方内容伪装成可登录顾客。

### 5.2 地区模型

每个地区只保存影响决策的字段：

- 所有者、控制者、核心归属、相邻地区。
- 人口、城市化、基础设施、补给中心等级。
- 民用工厂、军用工厂、资源产量。
- 地形：平原、丘陵、山地、森林、城市、荒漠之一。
- 战略价值、驻军、抵抗度、战争破坏度。
- 港口或海运通道标记。

“所有者”与“控制者”必须分开，战争占领不立即改变法理归属；和平协议后才转移所有权。

## 6. 一局的核心循环

每回合采用“获取信息 -> 同时规划 -> 锁定命令 -> 服务端结算 -> 查看报告”的循环：

```text
TURN_BRIEFING
  -> PLANNING
  -> COMMITTED
  -> RESOLVING
  -> TURN_REPORT
  -> 下一回合或 GAME_OVER
```

### 6.1 回合简报 `TURN_BRIEFING`

- 展示上回合结果、世界事件、市场价格、外交变化和当前危机。
- 第 1 回合展示国家优势、短板与 3 个建议目标。
- 该阶段不修改状态，只确认进入规划；单人可自动进入。

### 6.2 规划阶段 `PLANNING`

玩家可反复修改但尚未生效的计划：

- 调整税率、预算和产能分配。
- 新建、暂停或取消建设和征募队列。
- 发起贸易、改善关系、制裁、缔约和宣战提案。
- 修改法律或作出利益集团承诺。
- 给集团军指定战线、姿态、目标地区和补给优先级。
- 选择一个“国家重点”，为本回合提供集中加成。

所有修改都写入草案命令，只有点击“提交本回合”才锁定。使用同一 `clientRequestId` 重试不能生成重复建设、条约或军令。

### 6.3 提交与统一结算

- 单人局提交后，服务端为所有 AI 国家生成当回合命令并统一结算。
- 多人局所有有效真人提交后结算；房主可设置 60～300 秒期限，超时玩家沿用安全默认命令。
- 结算顺序固定且带版本号，不按 HTTP 请求到达顺序决定战争结果。
- 结算过程中接口返回 `RESOLVING`，不得重复触发；失败可由后台任务使用幂等键恢复。

### 6.4 回合报告 `TURN_REPORT`

报告只展示玩家在当时情报水平下应知道的信息：

- 国库、产出、价格、就业、稳定度和利益集团变化。
- 建设/征募进度与资源缺口。
- 战线推进、战斗伤亡、补给损耗和占领变化。
- 外交提案结果、条约、制裁与世界紧张度。
- 关键变化必须给出可解释的组成项，不能只显示“战力 -17%”。

玩家确认后进入下一回合。最后一回合或胜负条件触发时进入结算。

## 7. 经济系统

### 7.1 资源与产能

首版仅保留 5 种物资与 3 种能力：

| 项目 | 用途 |
| --- | --- |
| 粮食 | 人口消费、军队维持；短缺降低稳定度和兵员恢复 |
| 煤炭 | 民用工业、铁路与部分军工 |
| 钢铁 | 军备、工厂和基础设施建设 |
| 石油 | 机动集团军、空军支援和远距离补给 |
| 军需品 | 所有集团军补充与进攻消耗 |
| 民用产能 | 建设、消费品、贸易运输 |
| 军用产能 | 生产军需品和组建集团军 |
| 运输能力 | 国内补给与跨境贸易上限 |

不建立几百种商品。资源短缺不让生产瞬间归零，而是按满足率降低产出：

```text
投入满足率 = min(1, 实际可用投入 / 计划投入)
实际产出 = 基础产出 × 劳动力满足率 × 投入满足率 × 基础设施修正 × 稳定度修正
```

满足率最低保留一个很小的应急生产下限，防止一次短缺造成无法恢复的死锁；具体下限由平衡模拟确定。

### 7.2 人口与就业

不模拟单个 POP，只保存全国及地区聚合人口：

- 可劳动人口。
- 已就业人口。
- 失业人口。
- 已动员人口。
- 伤亡与自然增长。

动员会直接减少可劳动人口，提高军队上限，但降低税基和工厂吞吐。这样战争和经济使用同一人口约束，而不是两套无关数值。

### 7.3 财政

玩家每回合设置税率档位和三项预算：行政、民生、军事。

```text
财政收入 = 所得税 + 企业税 + 关税 + 条约收入
财政支出 = 行政 + 民生 + 军费 + 债务利息 + 建设付款
期末国库 = 期初国库 + 财政收入 - 财政支出
```

- 税率越高，短期收入越高，但消费、投资和利益集团支持下降。
- 民生预算影响稳定度、人口增长和工人支持。
- 军费不足会降低组织度恢复和补给效率。
- 国库不足时自动发行国债，但债务率过高会推高利率、通胀与进口成本。
- 首版不允许玩家手工选择债券期限，避免重复股票游戏的银行系统复杂度。

### 7.4 市场与贸易

世界市场按每种资源聚合当回合供需，价格使用有上限的平滑公式：

```text
稀缺率 = (全球需求 - 全球供给) / max(全球供给, 最小供给)
目标价 = 基准价 × exp(clamp(价格弹性 × 稀缺率, -上限, +上限))
本回合价格 = 上回合价格 × (1 - 平滑系数) + 目标价 × 平滑系数
```

贸易不是即时无限购买。贸易协定保存资源、每回合数量、价格规则、持续回合、运输需求和中断条件。战争、制裁、封锁或运输不足会按比例减少到货。所有国家先锁定合同，再统一计算市场，防止结算顺序偏置。

## 8. 政治与社会系统

### 8.1 国家指标

- 稳定度：影响税收、生产、征募与事件概率。
- 合法性：影响政策通过成本和政治行动点恢复。
- 战争支持度：影响宣战、动员、伤亡承受与求和压力。
- 行政能力：限制同时维持的法律、占领区和复杂条约。
- 世界威胁度：影响其他国家结盟、制裁和遏制倾向。

### 8.2 利益集团

首版固定 5 类：工业家、劳动者、军方、乡村群体、知识阶层。每组只有：

- 影响力 `0～100`。
- 支持度 `-100～100`。
- 当前诉求和最多一个临时承诺。

法律、预算、战争、失业和事件会改变支持度。高影响力且低支持度的集团可能触发罢工、投资撤离、军队不稳或政府危机，但结果必须通过有预警的危机进度条发生，不能无提示随机结束游戏。

### 8.3 法律

只设 4 个法律槽位，每槽 3 档：

- 经济组织：自由市场、混合经济、国家统筹。
- 劳工制度：低保障、基础保障、高保障。
- 兵役制度：志愿役、有限征兵、全面动员。
- 贸易制度：自由贸易、保护主义、战时管制。

每回合最多推动一项变更。通过概率由合法性、相关集团影响力、政治行动点和国家危机修正决定。玩家在提交前可看到预计通过率和失败代价；随机结果由服务端种子决定并写入审计。

## 9. 军事、战线与后勤

### 9.1 集团军而非师级微操

集团军是最小军事单位，字段包括：

- 所属国家、当前位置、目标战线。
- 人力、装备、组织度、经验。
- 兵种倾向：步兵、火力、机动三选一。
- 姿态：固守、均衡推进、重点突破、战略撤退。
- 补给优先级：低、标准、高。

国家通常控制 3～8 个集团军。新建集团军消耗人口、军需品和军用产能，并通过队列完成，不允许瞬间出现。

### 9.2 战线

当敌对国家控制的地区相邻时形成战线。玩家不逐格移动每支部队，而是：

1. 把集团军分配到一条战线。
2. 选择姿态和一个相邻目标地区。
3. 设置空中支援与补给优先级。
4. 服务端按双方命令同时结算战斗和推进。

一次结算最多使一个目标地区改变控制者，防止高战力在一回合穿越多个地区。撤退必须进入合法相邻己方地区；没有退路时产生额外投降损失。

### 9.3 战斗公式

公式应拆成可解释组件，而不是单一战力随机数：

```text
有效战力 = 基础兵力
         × 装备率
         × 组织度
         × 补给率
         × 地形修正
         × 指挥/经验修正
         × 姿态修正

进攻优势 = 进攻有效战力 / max(防守有效战力, 最小战力)
突破进度 = 基础推进 × 优势函数 × 空中支援 × 随机扰动
```

- 随机扰动使用截断分布且范围较小，优势方更可能获胜但不是绝对必赢。
- 防守方得到地形与工事修正。
- 重点突破提高当前进攻，但额外消耗组织、军需和石油，并削弱同战线其他地区。
- 伤亡同时扣减集团军人力和国家可动员人口。
- 每个结果保存全部修正项，回合报告可逐项解释。

### 9.4 补给

补给从首都或港口沿己方控制地区传播，每条边消耗运输能力：

```text
可达补给 = 源头供给 × 路径基础设施瓶颈 × 运输满足率 × 敌方干扰修正
集团军补给率 = min(1, 可达补给 / 集团军需求)
```

首版图只有 18 个地区，可使用 Dijkstra/最大瓶颈路径计算，不需要建立复杂铁路时刻表。路径和瓶颈必须展示在地图上，让玩家知道缺的是产量、运输还是道路。

### 9.5 海空军简化

- 空军是全国“空中支援点”，分配给战线后提供有限修正，消耗石油和军费。
- 海军是“海运保护/封锁点”，只作用于海上贸易与沿海补给。
- 不创建独立舰队、机型或空战回合；这些作为后续扩展，不影响首版陆战闭环。

## 10. 外交、战争与和平

### 10.1 可用行动

- 改善关系、施加外交压力。
- 提议贸易协定、互不侵犯、共同防御和军事通行。
- 实施制裁或禁运。
- 制造战争目标并宣战。
- 在战争中提出白和平、赔款、资源权或地区转移。

每项行动消耗外交点或政治行动点，并有明确冷却。多人提案需要对方在本回合接受；AI 按效用评分响应。

### 10.2 宣战限制

- 默认和平期内不能宣战。
- 必须拥有有效战争目标或在高世界威胁下承担额外惩罚。
- 低战争支持度宣战会立即降低稳定度。
- 互不侵犯条约未到期时破约会增加世界威胁和外交信誉损失。

### 10.3 和平

战争分数来自占领战略地区、战斗结果、封锁和战争疲劳。和平提案使用有限目标，不做自由拖拽式会议：

- 白和平。
- 赔款若干回合。
- 资源开采权。
- 转移一个有战争目标的地区。
- 强制解除制裁或退出战争。

战败不一定立即淘汰玩家。只要仍控制核心地区和政府合法性大于最低值，就可以继续经营；彻底失去核心地区才进入流亡/淘汰结算。

## 11. 国家重点、科研与事件

### 11.1 国家重点

每回合选择一个重点，避免复杂科技树和国策树：

- 工业扩建：提高建设速度。
- 民生恢复：提高稳定和人口恢复。
- 军备整顿：提高军需生产与组织恢复。
- 外交攻势：提高关系行动效果。
- 科研突破：积累科研点。
- 战时动员：提高兵员与运输，但伤害经济和支持度。

连续选择同一重点产生递减收益，鼓励根据局势切换。

### 11.2 科研

首版只设 12 项固定技术、4 条短路线：工业、社会、陆军、后勤。每项技术 2～4 回合完成，不能自由设计装备。剧本版本固定科技规则，发布后不可改变进行中场次。

### 11.3 事件

事件分为：世界事件、国家事件、利益集团危机、战争事件。事件选择必须基于公开条件和确定性种子；重要事件至少提前一回合显示条件或风险。选项展示立即效果与可能的后续方向，不提前暴露仍需掷骰的精确结果。

事件链保存链 ID、阶段、冷却和已选选项，不能只在当前回合 JSON 里覆盖，否则无法复盘。

## 12. AI 方案

### 12.1 为什么核心 AI 不使用大模型

军事策略每回合需要为多个国家规划财政、生产、外交和数条战线。把这些全部交给外部模型会带来超时、成本、不可复算、提示注入和模型读到隐藏信息等问题。核心 AI 应为本地效用 AI：

```text
候选行动效用 = 战略目标权重
             × 当前需求强度
             × 成功概率
             × 资源可承受度
             - 风险
             - 机会成本
```

### 12.2 AI 分层

- 国家战略层：安全、生存、工业、资源、扩张、联盟等目标权重。
- 预算层：先满足最低民生、军队维持和债务，再按战略目标分配剩余资源。
- 外交层：根据威胁、关系、信誉、共同敌人和资源互补选择条约。
- 军事层：识别危险战线，分配集团军，再在局部选择姿态和目标。
- 应急层：首都受威胁、粮食断供、债务危机时覆盖普通计划。

AI 只能读取本国可见情报，不能读取其他玩家未提交命令、完整库存或本回合随机结果。每次决策保存主要目标、候选效用和最终原因，供复盘与测试。

### 12.3 难度

- 简单：较大估值误差、较短规划视野，不获得数值加成。
- 标准：正常信息和 3 回合规划视野。
- 困难：更准确评估后勤、贸易和联盟连锁，仍不读取隐藏信息。

首版禁止用“AI 资源凭空增加”作为默认难度手段。若剧本需要挑战修正，必须在开局前明确展示并计入排名分组。

## 13. 胜负、评分与排行榜

### 13.1 游戏结束

满足任一条件后结束：

- 达到剧本回合上限。
- 某阵营完成剧本的决定性胜利条件。
- 只剩一个仍控制核心领土的国家/阵营。
- 房间成员一致同意提前结算。

### 13.2 综合国力评分

排行榜不能只按领土，否则经济与外交没有意义：

```text
综合国力 = 经济分 × 30%
         + 民生与稳定分 × 20%
         + 军事与战争目标分 × 25%
         + 外交与信誉分 × 15%
         + 科研分 × 10%
         - 债务危机、违约和无目标侵略惩罚
```

每个分项先归一化到 `0～1000`，最终分数保留整数。剧本可以调整权重，但同一 `versionLabel` 必须固定权重。排行榜绑定 `game_id + versionLabel + difficulty + countryCode + multiplayerFlag`，避免强国、弱国和不同难度直接混排。

当前 `game_leaderboard_entries` 的唯一键只有 `game_version_id + player_identity_key`，无法让同一玩家在不同国家/难度分组各保留一条成绩。需增加稳定的 `ranking_scope`，例如 `STANDARD:NORTH_REPUBLIC:SOLO`，唯一键改为 `game_version_id + ranking_scope + player_identity_key`。现有股票数据迁移为 `ranking_scope=DEFAULT`，股票排行语义不变。

### 13.3 结算页

- 胜负状态、综合分与各分项。
- 起始和最终版图对比。
- 国库、人口、工业、稳定度和军力时间线。
- 关键战争、条约、改革和转折事件。
- 同场国家排名与 AI 复盘。
- “同国家再来一局”和“更换国家”两个明确命令。

## 14. 创作者与剧本编辑器

### 14.1 MVP 的选择

最小可玩版本先发布系统维护的“裂洲纪元”，不开放任意地图编辑。原因是一个未校验的地图或国家配置很容易产生断开的补给图、无解资源短缺或 AI 无法行动。

### 14.2 第二阶段的受限编辑器

登录顾客可基于官方模板创建剧本，只允许：

- 选择预置地图模板和 3～6 个国家槽位。
- 修改国家/地区显示名、颜色和介绍。
- 在总预算约束内分配人口、资源、工厂和初始军力。
- 设置 12～36 回合、和平期、AI 难度和评分权重。
- 从官方事件库启停事件并调整允许范围内的权重。
- 设置单人/多人、人数上限、可见性、游玩密钥与版本标识。

不允许上传脚本、表达式或任意 SVG；地图只选择服务器内置模板。发布时执行静态校验和快速 AI 自走测试：地图连通、每国有核心地区、资源能形成最低闭环、首都可达、评分权重合计 100%、AI 能连续运行 5 回合无非法状态。

## 16. 后端多模式改造

### 16.1 模式元数据

扩展 `GameModeHandler`，至少返回：

```java
String displayName();

Set<String> capabilities();

```

`GuessStockModeHandler` 返回 `FINANCE`，新建 `GrandStrategyModeHandler` 返回 `STRATEGY`。`ModeResponse` 同步增加分类、路由键和能力，不在前端写死模式清单。

### 16.2 通用运行分派

新增独立运行接口，不把开始/同步/行动方法塞进配置校验器：

```java
public interface GameRuntimeHandler {
    String modeCode();
    Object start(Long gameId, PlayerIdentity player, JsonNode request);
    Object sync(Long sessionId, PlayerIdentity player);
    Object act(Long sessionId, PlayerIdentity player, String actionType, JsonNode payload, String requestId);
    Object pause(Long sessionId, PlayerIdentity player);
    Object resume(Long sessionId, PlayerIdentity player);
    void abandon(Long sessionId, PlayerIdentity player);
    Object leaderboard(Long gameId, PlayerIdentity player, Map<String, String> filters);
}
```

由 `GameRuntimeRegistry` 按 `games.mode_code` 或场次关联游戏分派。股票模式先用适配器包住现有 `GuessStockSessionService`，不在本次重写其价格引擎。

### 16.3 响应兼容策略

推荐新增 `/api/entertainment/v2` 通用会话契约，避免一次性破坏现有股票 Web 和未来移动端：

```json
{
  "id": 123,
  "gameId": 10,
  "modeCode": "GRAND_STRATEGY",
  "status": "ACTIVE",
  "turn": 4,
  "phase": "PLANNING",
  "serverTime": "2026-09-02T10:00:00",
  "modeState": {}
}
```

- 通用字段用于历史、路由、暂停和房间状态。
- `modeState` 由模式专属 DTO 序列化，前端按 `modeCode` 解码。
- V1 股票接口保留一版；股票 Web 迁移到 V2 并通过回归测试后再标记废弃。
- 不把军事字段继续追加到当前超大的 `EntertainmentDtos.SessionResponse`。

### 16.4 幂等与并发

- 命令保存以 `session_id + country_id + turn_no + command_type + client_request_id` 幂等。
- 提交回合对 `game_sessions` 加行锁，并用 `row_version` 防止重复结算。
- 结算任务幂等键为 `sessionId:turnNo:rulesVersion`。
- 多人最后一名提交和截止任务竞争时，只允许一个调用把阶段从 `PLANNING` 改为 `RESOLVING`。
- 随机结果只在第一次结算生成并保存；重试读取已有结果。

| 表 | 关键内容 |
| --- | --- |
| `grand_strategy_countries` | 场次内国家、控制者、国库、人口、政治指标、当前分数 |
| `grand_strategy_regions` | 地区所有者/控制者、人口、工厂、资源、设施、抵抗与破坏 |
| `grand_strategy_armies` | 集团军位置、战线、人力、装备、组织、经验、姿态 |
| `grand_strategy_turns` | 回合、阶段、世界价格、随机证据、结算状态、摘要 |
| `grand_strategy_commands` | 国家当回合草案/锁定命令、类型、载荷、幂等键 |
| `grand_strategy_build_queues` | 建设、征募、科研队列及投入进度 |
| `grand_strategy_relations` | 双边关系、威胁、信誉与外交冷却 |
| `grand_strategy_treaties` | 条约类型、参与方、起止回合、条款 JSON、状态 |
| `grand_strategy_wars` | 交战阵营、战争目标、战争分数、疲劳、状态 |
| `grand_strategy_battles` | 战线、参战方、公式分解、伤亡、推进与地区变化 |
| `grand_strategy_event_states` | 事件链、阶段、选择、冷却和完成状态 |
| `grand_strategy_turn_snapshots` | 国家视角回合快照、校验哈希和复盘摘要 |

对于 18 地区、6 国家、24 回合规模，关系型明细足以支撑查询和复盘。不要每次同步都从全量命令重放；读取当前状态表，同时用命令和快照做审计。

### 18.3 关键约束

- 每场每个国家代码唯一。
- 每场每个地区代码唯一，且任一时刻只有一个控制者。
- 每场每回合每个真人国家最多一个 `LOCKED` 命令包。
- 条约参与方不能相同，双边对称关系只保存一次规范化国家 ID 顺序。
- 集团军位置必须属于场次内地区；已淘汰国家不能创建新命令。
- 战斗、回合结算和排行榜插入均有唯一幂等键。
- 金额和比例使用 `DECIMAL`，人口和军队人数使用 `BIGINT`，禁止 `double` 直接落库。

通用 API：

```text

GET    /api/entertainment/games?category=STRATEGY&modeCode=GRAND_STRATEGY

DELETE /api/entertainment/v2/sessions/{sessionId}
GET    /api/entertainment/v2/games/{gameId}/leaderboard
```

军事模式高频查询可拆为只读资源，避免每次返回完整世界：

```text

GET /api/entertainment/v2/strategy/sessions/{id}/countries/{countryId}
GET /api/entertainment/v2/strategy/sessions/{id}/turn-report
GET /api/entertainment/v2/strategy/sessions/{id}/log?afterId=...
```

行动统一走通用 `actions`，示例：

```json
{
  "clientRequestId": "uuid",
  "actionType": "SAVE_TURN_PLAN",
  "payload": {
    "expectedTurn": 4,
    "expectedRevision": 7,
    "budget": {},
    "buildQueue": [],
    "diplomacy": [],
    "armyOrders": []
  }
}
```

保存计划使用 `expectedRevision` 做乐观锁；提交使用独立 `COMMIT_TURN`，提交后除非多人房间规则允许撤回，否则不能编辑。

## 20. 权威结算顺序

每回合固定按以下顺序结算，并把 `rulesEngineVersion` 写入回合：

1. 校验并冻结所有国家命令；缺失命令生成安全默认计划。
2. 处理到期条约、外交提案、宣战和阵营变化。
3. 锁定贸易合同并计算世界资源供需和价格。
4. 结算人口、就业、税收、预算、利息和通胀。
5. 结算资源开采、生产、建设、科研和征募进度。
6. 建立补给图，计算每条战线与集团军补给率。
7. 同时解析军事命令，结算战斗、伤亡、撤退和地区控制。
8. 结算占领、抵抗、战争疲劳、利益集团与法律。
9. 触发满足条件的事件并应用玩家已选结果。
10. 重新计算胜利条件、国家分数和淘汰状态。
11. 保存完整状态、玩家视角快照、报告、校验哈希并进入 `TURN_REPORT`。

影响同一指标的修正统一归集后再应用，不能让国家 ID 或数据库查询顺序决定结果。跨国贸易和战斗需要先计算意图，再整体落地。

## 21. 安全、公平与可恢复性

- 客户端永远不接收未侦察到的敌军精确数值、AI 未提交命令和未来随机结果。
- 地图接口按当前玩家视角生成；管理员调试视角必须使用独立权限，不能靠查询参数开启。
- 剧本配置做 JSON 深度、数组长度、文本长度和数值范围限制，拒绝任意脚本和外链资源。
- 所有写操作要求场次所有权/房间成员身份、当前阶段、当前回合和幂等键。
- 暂停只允许单人局；多人局使用断线托管/安全默认命令，不能让一名玩家暂停全房间。
- 单人恢复后读取持久化剩余阶段和已生成结果，不补跑离线回合。
- 每回合状态保存 `stateHash`；恢复和结算前校验，发现不一致时停止推进并记录告警。
- 排行榜只接受由服务端正常完成、使用公开允许配置且无数据校验错误的场次。

## 22. 测试与平衡

### 22.1 单元测试

- 每个纯引擎使用固定输入和固定种子断言精确结果。
- 经济守恒：资源来源、消耗和库存变化可对账。
- 人口守恒：就业、动员、伤亡之间不凭空增减。
- 地区唯一控制、集团军不能跨非相邻地区移动。
- 补给路径断开后不能继续获得满额补给。
- 条约到期、破约、宣战和和平状态转换合法。
- 同一命令和同一结算任务重复执行结果不变。
- 评分每个分项有上下界，不能出现 `NaN`、溢出或负无穷。

### 22.2 属性与模拟测试

至少定义 6 种场景：长期和平、资源危机、两强战争、联盟战争、债务危机、首都被围。每个场景使用多组种子自动运行：

- 快速 CI：每场景 100 局。
- 发布前完整校准：每场景 5,000～10,000 局。
- 任一标准 AI 国家不应因脚本错误连续 3 回合无合法命令。
- 24 回合完成率应为 100%，无死锁、负人口、重复地区归属或永不结束的 `RESOLVING`。
- 首发 6 国在标准 AI 自走中的夺冠率不应有国家低于 8% 或高于 30%；否则复核起始优势与评分。
- 战争不应在绝大多数对局第一回合和平期结束后立即全面爆发，也不应几乎从不发生。
- 资源价格与债务需设百分位护栏，极端值必须可由危机解释。

### 22.3 集成与并发测试

- 创建、发布、开局、暂停、恢复、完成和排行全链路。
- 股票与军事游戏混合分页、搜索、分类、历史和“我的游戏”。
- 最后一名玩家提交与超时任务并发，只结算一次。
- 双击提交、网络重试、结算进程重启、重复后台任务均不重复扣资源。
- 不同玩家同时提议/接受条约时保持一致。
- 旧股票场次、排行榜和 V1 接口行为不变。

### 22.4 Web E2E 与视觉检查

- 娱乐首页切换“全部 / 金融模拟 / 军事策略”，查询参数和卡片正确。
- 从军事卡片选国家、开局、保存计划、提交、查看报告、刷新恢复、完成结算。
- 地图缩放、平移、图层、键盘焦点与列表替代入口可用。
- 使用 Playwright 检查 1440×900、1024×768、390×844；不得出现指标重叠、抽屉挡住提交按钮或文字溢出。
- 对地图截图做非空像素检查，确保地图资产加载失败时测试能发现，而不只是页面 HTTP 成功。

## 23. 性能目标

以 6 国家、18 地区、48 个集团军、24 回合为基准：

- 普通同步接口 P95 小于 300ms，不含网络。
- 单回合纯规则结算 P95 小于 500ms，含落库整体 P95 小于 1.5s。
- 地图初始有效载荷 gzip 后目标小于 300KB；静态拓扑按版本缓存。
- 同步使用差量日志和版本号，不在每次轮询返回 24 回合完整历史。
- 单个场次全部结构化数据和快照设置合理上限，防止恶意剧本造成无限增长。

若结算超过同步请求预算，`COMMIT_TURN` 返回任务状态，前端轮询或通过现有 WebSocket 能力接收完成事件；不能让浏览器无限等待。

## 24. 分阶段实施计划

### 阶段 A：多模式地基，3～5 人日

- 扩展模式元数据、游戏分类与 SQL 前置筛选。
- 新增通用运行注册表与 V2 会话外壳。
- 用适配器接入股票模式，保持现有功能和 V1 契约。
- 改造娱乐首页分类、通用卡片、创建模式选择和按模式路由。
- 增加股票回归测试。

验收：同一娱乐首页能显示两个模式占位卡；分类、分页、详情和路由不混淆；股票游戏全部可继续游玩。

### 阶段 B：可自走规则内核，7～10 人日

- 定义官方地图、国家、地区和配置 schema。
- 建立场次国家/地区/回合/命令/快照表。
- 实现经济、生产、人口、财政、贸易与评分纯函数。
- 实现标准 AI 的预算和生产规划。
- 实现无 UI 的 24 回合自走模拟与守恒测试。

验收：6 个 AI 国家可用固定种子连续完成 24 回合并输出一致结果。

### 阶段 C：战争、后勤、外交与政治，10～15 人日

- 实现地图邻接、集团军、战线、补给和战斗。
- 实现条约、宣战、战争目标、和平与制裁。
- 实现利益集团、法律、危机、国家重点、科研和事件链。
- 完成 AI 军事、外交与应急规划。
- 增加完整结算顺序、回合报告和复盘明细。

验收：资源短缺能通过贸易或占领改变战略；战斗结果能解释到补给、地形、组织和姿态；战争可合法结束。

### 阶段 D：单人 Web 完整体验，8～12 人日

- 完成详情、国家选择、主地图、各管理面板、计划提交和报告。
- 完成暂停、恢复、断线恢复、结算与排行榜。
- 完成独立玩法说明和响应式布局。
- 增加 E2E、截图与地图像素检查。

验收：新用户不看外部文档也能从娱乐首页完成一局；所有关键失败都有明确原因和下一步。

### 阶段 E：多人和受限剧本编辑器，8～12 人日

- 让通用房间按模式分派开始和同步。
- 增加同时规划、准备状态、超时默认命令、断线托管和重新加入。
- 开放模板式剧本编辑器、发布校验和 5 回合自走预检。
- 排行榜增加国家、难度和单/多人分组。

验收：2～4 真人可完成一局；重复提交或断线不造成重复结算；不合法剧本不能发布。

### 阶段 F：平衡、灰度与文档，5～8 人日

- 完整批量校准、性能测试、安全检查和兼容回归。
- 使用功能开关仅向测试用户开放，再开放官方剧本，最后开放玩家创建。
- 补充运维指标、数据库回滚脚本、后端说明书和手机端待开发清单。

总量预估：单人官方剧本 MVP 约 30～45 人日；连同多人、受限编辑器和完整灰度约 50～70 人日。单人全栈开发约 10～14 周，前后端并行可缩短自然周，但不能省略平衡模拟和兼容回归。

## 25. 功能开关与发布策略

建议增加：

```text
entertainment.multiModeHub
grandStrategy.enabled
grandStrategy.multiplayer
grandStrategy.creatorEditor
grandStrategy.leaderboard
```

发布顺序：

1. 在测试环境启用多模式首页，但军事卡片仅内部可见。
2. 开启单人官方剧本，不开放排行榜，观察错误率、回合完成率与平均时长。
3. 固定规则版本后开启排行榜。
4. 开启多人房间。
5. 最后开放玩家模板剧本创建和发布。

回滚时只关闭功能开关，不删除军事表或改写历史。已经开始的场次可暂时只读，待重新开启后恢复；明确存在规则错误的版本标记不可新开局，但历史复盘仍可读取。

## 26. 监控指标

- 按模式统计详情到开局转化、开局到完成转化、平均回合数、平均时长和放弃阶段。
- `RESOLVING` P50/P95/P99、失败数、重试数和超过 10 秒未完成数。
- 幂等冲突、状态哈希不一致、非法命令、恢复失败与重复排行榜拦截数。
- 按国家和难度统计胜率、平均综合分、破产率、宣战回合、战争持续时间和资源短缺回合。
- Web 地图资源加载失败、前端未捕获错误和移动端抽屉操作放弃率。

指标只记录游戏状态和技术信息，不把私人房间名称、密钥、自由文本或用户令牌写入日志。

## 27. 明确不做与后续候选

首版明确不做：

- 真实世界地图和历史国家。
- 即时制与小时级时间推进。
- 逐师编制、装备设计、独立海空战棋盘。
- 数百商品、逐 POP 模拟、移民和复杂选举。
- 任意地图上传、脚本事件和创作者公式。
- 大模型直接控制 AI 或裁决战斗。
- 跨场次元货币、付费道具或真实奖励。

验证核心玩法后可评估：战争迷雾侦察、谍报行动、内阁人物、更多地图模板、合作阵营模式、观战与回放、异步长局、原生手机端以及只生成叙事文本的可选大模型。

## 28. 最终验收清单

产品验收：

- 股票游戏与军事策略游戏出现在同一个娱乐页面，并以一级分类明确区分。
- 搜索、分类、分页、详情、创建、历史和排行榜不会读取错误模式字段。
- 官方军事剧本可以选国、开局、完整游玩、保存恢复并结算。
- 经济、政治、外交、战争和后勤都至少产生一种可感知且互相影响的决策。
- 一局标准配置可在 30～60 分钟内完成。

技术验收：

- `EntertainmentController` 的通用场次入口不再硬编码只调用股票服务。
- 股票旧游戏、旧场次、排行榜和价格结果通过回归测试。
- 军事结算由服务端权威执行，固定种子可复算，重复请求不重复结算。
- 全部关键数值有范围校验，全部状态变化有命令或结算记录可追溯。
- 6 场景快速模拟、完整校准、后端测试、Web 构建、E2E 和桌面/移动截图检查通过。
- 功能开关、监控、数据库迁移及回滚说明齐全。

## 29. 建议的第一批实现任务

正式开工时优先拆成以下可独立评审的任务，避免一个超大变更同时修改股票和军事规则：

1. 扩展模式元数据与娱乐首页一级分类，修复列表 SQL 前置筛选。
2. 增加 V2 会话外壳、`GameRuntimeRegistry` 和股票适配器。
3. 提交“裂洲纪元”地图/国家 schema、校验器和只读详情页。
4. 提交经济、财政、人口和生产纯引擎及自走测试。
5. 提交贸易、市场、政治、科研和事件引擎。
6. 提交集团军、补给、战斗、外交和和平引擎。
7. 提交 AI 规划器与六场景批量校准。
8. 提交军事单人场次服务、迁移、暂停恢复和结算。
9. 提交地图工作台、管理面板、回合报告和响应式交互。
10. 提交多人房间适配、受限编辑器、灰度开关与运维文档。

第一批只先做第 1～4 项即可形成可信的技术纵向切片；确认自走经济和多模式地基稳定后，再把战争、多人和编辑器叠上去。
